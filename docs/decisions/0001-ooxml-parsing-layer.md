# ADR 0001：OOXML 解析层由我们自己实现

- 状态：已采纳
- 日期：2026-11-22
- 依据：Phase 0 关卡 G4，见 [`spikes/g4-ooxml/README.md`](../../spikes/g4-ooxml/README.md)

## 背景

DOCX、XLSX、PPTX 文件里有大量我们第一版不会建模的内容：批注扩展、修订、注音、VML 后备、迷你图、切换效果、第三方写进去的扩展元素。用户用我们的软件打开一个文件、改一个字、保存，这些内容必须原样留在文件里。方案把这个目标分成三级：

- **包级**：没有被触碰的部件按原始字节写回。
- **元素级**：解析时不认识的元素和属性作为不透明节点挂在所属的模型节点上，随节点移动，随节点删除。
- **语义级**：已建模的内容由我们序列化。

G4 要决定的是由谁来做解析和写回：采用现成的库，还是自己写。候选是 BetterOffice 0.5.1、ooxmlsdk 0.15.0 和 office_oxide 0.1.17。

## 决定

**包的读写和未知内容的保真由我们自己的层负责，基于 quick-xml 和 zip 实现。不把任何一个候选库作为模型或保存路径。**

具体是：

1. 包读进来是一组按原始字节保存的部件。保存时，没有被修改的部件原样写回，**关系部件和 `[Content_Types].xml` 也在内**。只有内容确实变了的部件才重新生成。
2. 已建模的部件由我们自己的解析器读成模型。解析器遇到不认识的元素或属性，不丢弃，作为不透明节点挂在模型节点上。
3. 写回已建模的部件时，认识的内容由我们序列化，不透明节点按原样输出。

三个候选库的位置：

| 库 | 位置 |
| --- | --- |
| BetterOffice | 仍是 XLSX 和 PPTX 编解码器的候选，是否采用不在本决定之内。若采用，只通过 `FormatCodec` 接入，锁定精确版本。DOCX 不采用 |
| ooxmlsdk | 不作为产品依赖。它生成的类型可以在写解析器时当作模式的参考 |
| office_oxide | 与 G4 之前相同：只用于旧格式导入、全文索引和预览 |

## 理由

数据来自 G4，三份手写样本加 BetterOffice 自带的 128 个测试文件。

- **只有自己的层在三种格式上都达到了“没有改动的部件逐字节不变”。** 它目前只是一个不建模任何内容的最小实现，但证明了目标可以达到，而且做法简单：不碰的东西不重写。
- **BetterOffice 的 DOCX 每次保存都从模型重写正文。** 不做任何修改直接保存，注音连同基字、文本框的 VML 后备和若干格式属性就丢了。它的 XLSX 和 PPTX 没有这个问题。
- **ooxmlsdk 保不住模式之外的内容。** 模式里有的它都能保住，但第三方扩展元素一解析就被丢弃，而这正是元素级保真要防的情况。它还直接拒绝打开不合模式的文件，办公软件必须能打开别的程序写出的不太规范的文件。
- **“内容等价”的重写不等于安全。** ooxmlsdk 重新生成的内容类型列表是合法的 XML，内容与原文件相同，但 macOS 的“快速查看”读这样的 XLSX 会卡住。所以第 1 条把关系部件和内容类型列表也纳入“原样写回”。
- **依赖的代价。** ooxmlsdk 单个编译进程的内存峰值是 7.3 GB，BetterOffice 带来 110 个 crate。自己的层从零构建 3.6 秒。

## 后果

好的一面：

- 保真的行为由我们自己的代码和测试决定，不随第三方库的版本变化。
- 写回路径上没有“我们不知道它会不会重写”的环节。
- 主工作区不增加大体量的依赖。

要承担的：

- 每一种要建模的部件都要自己写解析和序列化，模式知识的成本在我们这边。这是 Writer、Sheets、Slides 各自工期里的固定一项。
- 元素级保真目前只有设计，没有实现。G4 的最小层只验证了包级保真和“改一处文字”。不透明节点随模型节点移动和删除的行为，要在写第一个真实模型时实现并测试。
- “打开后不修改直接保存”的往返测试要成为 CI 的常驻项，覆盖整个兼容性语料库。G4 的比较器和结构检查可以直接沿用。
- 保存编辑过的工作簿时，除了改动的工作表和 sharedStrings，还可能改 styles.xml：在“常规”单元格里输入日期、时间、百分比、金额或千分位数字时，像 Excel 一样自动套格式，工作簿里没有对应格式就在 `numFmts` 和 `cellXfs` 末尾追加，其余字节不动。这是用户 2026-11-24 的决定。从工具栏改格式时同样在 `fonts`、`fills`、`borders`、`cellXfs` 末尾追加。增删公式时还会删掉 calcChain.xml 及其关系和内容类型。插入删除行列时，被移动的行和单元格保留原字节、只换 `r` 属性，移动过的表里的公式单元格整个重写，定义名称和绘图部件的锚点跟着移动；增删和改名工作表时改 workbook.xml、它的关系和内容类型，新表新增部件，删掉的表去掉部件，图表和 `docProps/app.xml` 里的表名跟着改名。

## 这个决定的边界

G4 还不算通过，下面两条没有验证，所以这个决定是在不完整的证据上做的：

- 没有用 Microsoft Office 打开过任何产物。
- 样本是手写的和程序生成的，不是 Office 保存的真实文件。

这两条补上之后，如果出现下面任何一种情况，应当重新审视：

- 真实文件上，自己的层在不修改时也做不到逐字节写回。
- Microsoft Office 对我们原样写回的包给出修复提示。
- BetterOffice 或 ooxmlsdk 的后续版本提供了可靠的未知内容保留，并且维护状况明显改善。

## 没有在这里决定的

- BetterOffice 是否作为 XLSX 和 PPTX 的编解码器。G4 的数据支持它作为候选，它还有一个注音文字混进图表缓存的错误要先处理。
- 公式引擎，由 G5 决定。
- 旧版 DOC、XLS、PPT 和 ODF 的处理方式，属于方案的待决策事项。
