# ADR 0002：计算引擎以 formualizer 为第一候选

- 状态：已采纳
- 日期：2026-11-22
- 依据：Phase 0 关卡 G5，见 [`spikes/g5-formula/README.md`](../../spikes/g5-formula/README.md)

## 背景

Sheets 需要一个公式引擎：解析公式、跟踪依赖、在单元格变化后把结果算出来。方案给它定的预算是“单格编辑后可见区域结果刷新 100 毫秒以内”，G5 的通过标准是在 10 万个公式的工作簿上，单格修改后重算的 95 分位不超过 100 毫秒，结果与 Excel 一致。

自己写一个与 Excel 兼容的公式引擎是以年计的工作，所以要先看现成的能不能用。候选是 formualizer 0.15.0、IronCalc 0.9.1 和 BetterOffice 0.5.1 自带的计算引擎。

## 决定

**以 formualizer 为计算引擎的第一候选，接在 `CalcEngine` 接口后面。IronCalc 作为备选。BetterOffice 的计算引擎不采用。**

具体是：

1. 引擎只通过 `CalcEngine` 接口的一个实现接入，放在适配器 crate 里，核心 crate 不直接依赖它。
2. 单元格的输入以我们的 `SheetsModel` 为准。引擎持有的是派生状态，可以随时从模型重建。
3. 重算在后台线程进行，可以取消。界面在结果回来之前显示旧值。
4. 版本锁定到精确版本。升级时重跑 G5 的测量和 69 个公式的对照。

“第一候选”的意思是：Sheets 的开发以它为目标，但在下面“转为正式依赖之前要补的”几项完成前，它不进入发布版本的依赖清单。

## 理由

数据来自 G5，三个各有 10 万个公式的工作簿，单格修改后重算的 95 分位，单位毫秒：

| 引擎 | 改一格波及 8 格 | 改一格波及全部 | 5 万个 VLOOKUP |
| --- | --- | --- | --- |
| formualizer | 2.1 | 14.2 | 19.0 |
| IronCalc | 23.9 | 10.2 | 2,351 |
| BetterOffice 的引擎 | 13.7 | 116.4 | 结果错误 |

- **formualizer 是唯一三项都达标的。** 它在两次调用之间保留依赖图，只算受影响的单元格；工作簿放大到 100 万个公式时，只波及少数单元格的修改仍是 12 毫秒。
- **它有取消和分步执行的接口。** 这与决定里的第 3 条直接对应。另外两个引擎都没有取消，用它们就只能等一次重算跑完。
- **IronCalc 每次全量重算。** 简单算术上它很快，10 万个公式 10 到 24 毫秒，内存也最省。但它的精确匹配查找是线性扫描，每次修改全部重来，查找密集的工作簿每次要 2.4 秒。这类工作簿在财务和进销存里很常见，所以它不能做第一候选。
- **BetterOffice 的引擎有一个改不了的上限。** 每次重算最多读一千万次单元格，超过后剩下的公式保留旧值而不报错。在查找工作簿上，10 万个公式里有 80,113 个没有算。算错而不自知，比算得慢更不能接受。
- **与 Excel 行为的对照三者相近。** 69 个小公式里 IronCalc 相符 68 个，formualizer 66 个，BetterOffice 65 个。这不足以区分它们，也没有哪个差到要排除。

## 后果

好的一面：

- Sheets 的第一版不需要自己写公式引擎。
- 增量重算和取消是引擎自带的，不是我们要补的。
- 引擎在 `CalcEngine` 后面，换掉它不影响模型、命令和界面。

要承担的：

- **项目很新。** formualizer 创建不到一年。它停止维护或大改接口的可能性是这个决定最大的风险。应对是第 1、2 条：只通过适配器接入，模型不依赖它。
- **依赖重。** 它带来 139 个 crate，主要是 Apache Arrow，从零构建 71 秒。
- **有三处与 Excel 不符的行为要在适配器里处理或向上游报告**：`0.1+0.2=0.3` 给出 FALSE，`VALUE("1,234")` 报错，`LAMBDA` 的直接调用未实现。
- **日期是独立的类型。** 它的 `DATE()` 返回日期值而不是序列号，适配器要负责转换，否则日期运算的结果类型会与 Excel 不同。

## 转为正式依赖之前要补的

G5 还不算通过。下面几项完成之前，这个决定只约束开发方向：

1. **与 Excel 对照。** 用 Excel 打开 G5 的三个工作簿核对结果，并把 69 个公式在 Excel 里跑一遍。期望值目前是按 Excel 的既定行为写下的，不是运行得来的。
2. **实测取消。** 取消接口是读代码确认存在的。要验证：取消之后工作簿处于什么状态，能否继续编辑和重算，已算出的部分是否可信。
3. **补上没有测的操作。** 改公式、批量粘贴和填充、插入和删除行列、易失函数、数组溢出、循环引用。这些会改变依赖图本身，G5 只测了改数值。
4. **许可证。**（2026-11-23 已解决：项目负责人接受 CC0-1.0，formualizer 经 `aster-calc` 接进了只读的 Sheets 标签。下面是原文。） 它的依赖里有一个只有 CC0-1.0 许可证的包（`tiny-keccak`，经 Apache Arrow 在部分目标平台上进来，只在编译期使用）。CC0 是方案里需要法务确认的四项之一。
5. **在 Windows 和 Linux 上重跑 G5。**

## 什么情况下改用备选

出现下面任何一种情况，改用 IronCalc，并接受随之而来的工作量：

- 第 1 到 3 项里发现 formualizer 有算错的情况，且上游不修。
- 取消之后工作簿状态不可恢复。
- 项目停止维护，或接口的变动频繁到适配器跟不上。

改用 IronCalc 意味着：全量重算放到后台线程；自己给它补精确匹配查找的索引；没有取消，一次重算只能等它跑完，所以还要给超大工作簿的重算设上限或分批。方案里把“增量重算”列为那种情况下的自研项，这一条不变。

## 没有在这里决定的

- BetterOffice 是否作为 XLSX 的编解码器。若采用，重算交给这里选定的引擎，不用它自带的。
- 自定义函数、宏和脚本，不在第一版范围内。
- 引擎结果与我们自己的数字格式、日期系统设置之间的对应关系，属于 Sheets 的设计。
