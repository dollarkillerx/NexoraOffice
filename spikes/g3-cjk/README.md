# G3：中日文段落排版

Phase 0 的第三道关卡。要回答的问题：在 Parley 的整形结果之上，能不能用我们自己的断行器实现中文和日文的排版规则，并且在三个系统上断出完全相同的行。

## 做法

分工是这样的：

- **Parley** 只负责整形和字体回退。让它把整段排成不换行的一行，取出每个字符簇的宽度和字形。
- **ICU4X** 给出哪里允许断行。使用 UAX #14 的严格模式，并按内容语言调整，这一层保证了句读点、闭合括号、小假名和长音符号不会出现在行首，开括号不会留在行尾。
- **`breaker.rs`** 是我们自己的断行器。它不知道字体的存在，只接收“宽度加能否在此断行”的字符簇，决定每行在哪里结束、每个字符放在哪里。

断行器实现了五条规则，每条都可以单独开关：

| 规则 | 作用 |
| --- | --- |
| 连续标点挤压 | 全角标点自带半个字宽的空白，两个标点相邻时去掉多余的空白，使它们之间最多留半个字宽 |
| 行尾标点挤压 | 行尾的闭合标点让出空白的那一半，让这一行能多放半个字 |
| 行尾悬挂 | 挤压后仍放不下的逗号和句号可以挂到版心之外 |
| 中西文间距 | 汉字、假名与拉丁字母、数字相邻处插入四分之一字宽 |
| 两端对齐 | 把剩余空白分摊到词间空格和中日文字符之间，不会把标点和它所属的文字拉开 |

所有宽度计算用 1/64 像素的定点整数，不用浮点数。断行的判断是“若干宽度之和与行宽比大小”，用整数做就不依赖各平台的浮点舍入。

## 运行

```sh
cargo run -p g3-cjk -- lines 18             # 样张在 18 字宽下怎样断行（合成度量，不依赖字体）
cargo run -p g3-cjk -- digest               # 一个摘要值，三个系统上必须相同
cargo run -p g3-cjk -- compare 18           # 真实字体下，Parley 自带断行与自研断行器逐行对比
cargo run -p g3-cjk -- png out.png 18       # 把同样的对比画出来
cargo test -p g3-cjk
```

`lines` 输出的每行开头是三个标记：断行原因（`S` 正常断行、`H` 换行符、`E` 段落结束、`!` 强制截断）、行尾处理（`C` 挤压、`G` 悬挂）、是否两端对齐（`J`）。

## 结果

在 macOS 27.0.1 上，2026-11-22：

- 28 个测试通过。其中一个性质测试对 5 个样张在 4 到 39 字宽的每一种行宽下检查：文字不丢不重、行首没有闭合标点、行尾没有开括号、没有行超宽、对齐的行正好贴齐右边。
- 真实字体下与 Parley 自带断行逐行对比，26 行里 21 行断在同一处。不同的 5 行全部在中文样张里，原因是标点挤压让每行多放了字，整段少用一行。对比图见 `comparison.png`。
- 摘要值是 `0x8515cd8a10c36b74`，已写进测试。Windows 和 Linux 上跑 `cargo test -p g3-cjk` 时，这个测试通过就说明断行结果逐字节相同。

## 这道关卡还没有通过

两项通过标准里，一项只完成了一半，一项没有做：

- **三个系统上断行结果一致**：只在 macOS 上跑过。跨平台的检查手段已经就位（合成度量加摘要测试），但还没有在 Windows 和 Linux 上运行。使用真实字体时，还需要三端使用同一份字体文件，这要等内置字体做完。
- **与 Word 逐行对照**：没有做。这台机器上没有 Microsoft Word，需要有人用 Word 把同样的样张按同样的字体和版心排出来，导出 PDF 作为对照。

## 实测中发现的问题

- **Parley 的公开接口不提供断行机会**。从 `Layout` 里能拿到字符簇的宽度和字形，但拿不到“这里是否允许断行”，所以断行机会是直接向 ICU4X 要的。Parley 0.13 用的也是同一版 ICU4X，数据只链接一份。
- **没有用到 `parley_engine`**。方案原本设想从它接入。它要求调用方自己实现字体选择，文档还写着“断行后的重新整形仍在开发中”。这次走的是 Parley 的公开 `Layout` 接口，已经够用；`parley_engine` 这条路只读了源码，没有验证。
- **中文里的弯引号来自西文字体**。`“ ”` 在 Unicode 里中西文共用，Parley 先在西文字体里找到了它，于是它是窄的比例宽度，不是全角。断行器检测到宽度不足一个字宽就不对它做挤压。正式实现需要按内容语言为这几个符号指定字体。
- **挤压量是按“空白在哪半边”硬编码的**。这对简体中文和日文字体成立，对标点居中的繁体中文字体不成立。正式实现应当使用字体自带的 OpenType 特性（`halt`、`chws`）。
- **不可断开的长串会让前一行被拉得很松**。日文样张里“（ゃ・ゅ・ょ・っ）、”整串不能断，前一行只剩 12 个字却被拉满 18 字宽。需要有“把后面的字挤进来”的策略，或者给拉伸量设上限。
- **断行算法是逐行贪心的**，每试一个断点都重新累加整行宽度。样张够用，长段落需要改成增量计算。

## 没有覆盖的内容

竖排、注音、连字符断词、从右到左的文字、制表位、行内图片，以及分页。
