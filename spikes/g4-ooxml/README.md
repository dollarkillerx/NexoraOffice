# G4：OOXML 往返

Phase 0 的第四道关卡。要回答的问题：一个 DOCX、XLSX 或 PPTX 文件被打开再保存之后，原来的内容还剩多少；用哪个库做解析层，才能做到“没有改动的部件逐字节不变”。

## 结论

- 关卡的标准只有我们自己写的最小层在三种格式上全部达到。它不建模任何内容，只证明目标可以达到。
- **BetterOffice 0.5.1** 的 XLSX 和 PPTX 达到了标准，DOCX 没有：不做任何修改直接保存，注音、文本框的后备内容和若干格式属性就丢了。
- **ooxmlsdk 0.15.0** 不碰的部件原样写回，碰过的部件按类型模型重写。重写时模式里有的内容都能保住，模式里没有的外来元素会被丢掉。它对不合模式的文件直接拒绝打开。
- **office_oxide 0.1.17** 的编辑接口是在原始 XML 上做字符串替换，没有模型，没有可采用的东西。
- 决定：包和未知内容的保真由我们自己的层负责，不交给任何一个候选库。BetterOffice 仍可作为 XLSX 和 PPTX 编解码器的候选。已于 2026-11-22 采纳，见 [ADR 0001](../../docs/decisions/0001-ooxml-parsing-layer.md)。

这道关卡**还不算通过**：这台机器上没有 Microsoft Office，“产物能无修复提示打开”这一条没有验证；样本也不是 Office 生成的真实文件。见“为什么还不算通过”。

## 做法

每个候选库实现同样的两个操作：

- **重存**：打开文件，不做任何修改，保存。
- **编辑**：做一处最小的修改再保存。DOCX 改第一段文字，XLSX 改第一个工作表里第一个纯数字单元格，PPTX 改第一张幻灯片的第一段文字。

然后把产物和原文件逐个部件比较。比较的是部件解压后的内容，不是 zip 容器。

| 判定 | 含义 |
| --- | --- |
| `pass` | 没改的部件逐字节相同，被改的部件除了那一处修改没有丢任何东西。这是关卡的标准 |
| `rewritten` | 没有丢东西，但没改的部件被重新写了一遍，字节不同 |
| `LOSSY` | 原文件里的元素、属性、文字或整个部件不见了，或属性值被改成了别的意思 |
| `INVALID` | 产物有原文件没有的结构错误：悬空的关系、缺内容类型、XML 不合法、命名空间前缀没声明 |
| `FAILED` | 库拒绝打开、崩溃，或保存的结果里找不到那处修改 |

两个 XML 部件“内容相同”的定义：元素的顺序、带命名空间的名字、属性值和文字都相同。命名空间前缀怎么起、属性的先后、XML 声明和元素之间的空白不算。

下面几种差异不算丢失，规则都写在 `src/compare.rs` 和 `src/run.rs` 里，各有测试：

- 属性值换了写法但意思一样：`1` 和 `1.0`，`true` 和 `1`，`mc:Ignorable` 多列了几个前缀。
- 省略了等于默认值的属性：`<w:cantSplit w:val="1"/>` 写成 `<w:cantSplit/>`。只认样本里实际遇到的那几种。
- 去掉了空的属性容器：`<w:pPr></w:pPr>`。
- 改了单元格之后，公式的缓存结果、图表缓存里的数字跟着变。
- 改了单元格之后删掉 `calcChain.xml`，连同它的关系和内容类型。

结构检查在 `src/validate.rs`。它查的是会让 Office 提示“修复”的那类错误，但不按模式校验每个部件，所以比真的用 Office 打开要弱。

### 候选

| 名称 | 是什么 |
| --- | --- |
| `own layer` | 我们自己的最小层。包是一组按字节保存的部件；编辑时把目标部件当作 XML 事件流重写，除了目标之外原样通过。这是方案里写的备选方案“基于 quick-xml 自写解析层”的雏形 |
| `betteroffice` | BetterOffice 0.5.1 的三个门面 crate |
| `ooxmlsdk` | ooxmlsdk 0.15.0，只解析编辑要碰的那个部件。这是它的最好情况 |
| `ooxmlsdk/all` | 同一个库，打开时解析全部部件。编辑器把它当模型用时就是这种情况 |
| `office_oxide` | office_oxide 0.1.17 的编辑接口 |

### 样本

`corpus/` 下有三份手写的样本，以带缩进的 XML 目录存放，运行时打成包并去掉缩进。里面特意放了库容易丢的内容：

- **DOCX**，24 个部件：批注、脚注和尾注、修订（插入与删除）、域、书签、超链接、带合并单元格的表格、图片、`mc:AlternateContent` 文本框及其 VML 后备、绑定到自定义 XML 的内容控件、公式、注音、`w14` 和 `w15` 扩展属性、一个外来命名空间的元素、一个类型未知的二进制部件。
- **XLSX**，20 个部件：带注音和富文本的共享字符串、共享公式、定义名称、条件格式、数据验证、表格、图表、批注及其 VML、迷你图扩展、`calcChain`。
- **PPTX**，26 个部件：母版与两个版式、备注母版与备注页、图片、表格、组合形状、连接线、`mc:AlternateContent` 里的切换效果、动画节点、`extLst` 扩展。

这三份样本是为这道关卡写的，不是 Microsoft Office 的输出。它们能被 macOS 自带的导入器读取（`textutil` 读出了 DOCX 的全部文字，“快速查看”给三份都生成了缩略图），这只说明它们大体合法。

另外用了 BetterOffice 随 crate 一起发布的 128 个测试文件做对照，它们同样是程序生成的。这些文件不在本仓库里，运行时从 cargo 的下载目录读取。

没有 Office，只能用 macOS 的“快速查看”给内置样本的产物生成缩略图当作冒烟测试。试过的 18 个产物里，BetterOffice 和 office_oxide 的各 6 个、`own layer` 的 1 个、ooxmlsdk 的 DOCX 和 PPTX 都正常，ooxmlsdk 的 XLSX 卡住，原因见下面 ooxmlsdk 一节。

读这张表要知道三件事：

- `own layer` 的 6 个 FAILED 是文件里没有可改的东西：5 个演示文稿的第一张幻灯片没有文字，1 个工作簿没有纯数字。其他候选在同样的文件上也失败。
- `LOSSY` 是自动判定，会多报。它不认识模式里的全部默认值，所以“省略了默认值”有时也被算成丢失。下面各节列的是我逐个看过、确认是真的那些。
- 这批文件是 BetterOffice 自己的测试数据，多数没有 `w14:paraId`，这一点对它的 DOCX 编辑接口很不利，见下。

## 各候选的发现

### BetterOffice

**XLSX 和 PPTX 做得对。** 不修改时，XLSX 直接返回原始字节，PPTX 每个部件逐字节相同。改一个单元格之后，它重算了依赖的 5 个单元格，更新了另一个工作表和图表里的缓存值，删掉了 `calcChain` 并在工作簿上标记了打开时重算，没碰的部件保持原样。PPTX 改一段文字后只有那一张幻灯片变了。

**XLSX 有一个与日文有关的错误。** 改单元格后重建图表缓存时，带注音的字符串被写成了 `東京トウキョウ`，注音文字混进了正文。原文件里这个值是 `東京`。

**DOCX 每次保存都从模型重写**正文、页眉页脚、脚注尾注和批注，即使什么都没改。在我们的样本上，不修改直接保存就丢了：

- 注音（`w:ruby`）整个不见了，连同基字“東京”，原处只剩一个空的 `w:r`。
- `mc:AlternateContent` 被拆掉，只保留了 `Choice` 分支，VML 后备分支没有了。
- `w14:ligatures`、`w:noProof`，以及图片锚点上的 `wp14:anchorId` 和 `wp14:editId`。
- 图片的名字从 `Picture 1` 被改成了 `image1.png`。在它自己的测试文件里也有 7 个文件的图片名字被这样改掉，另有 7 个文件的图片编号从 `0` 变成 `1`。

它还会添加原文件没有的三个批注扩展部件。

**DOCX 的编辑接口很窄。** 只能按 `w14:paraId` 整段替换文字，而且这一段必须是空的，或者只有一个纯文字的 run。我们的样本里前三个有文字的段落都被拒绝了（带书签的标题、多个 run 的正文、带批注的句子），第四段才改成。它自己的 104 个 DOCX 测试文件里有 102 个没有 `w14:paraId`，一段都改不了。Word 2010 之后保存的文件带这个属性，LibreOffice、Google 文档和更早的 Word 生成的文件没有。

### ooxmlsdk

**部件按需解析，没解析的原样复制。** 所以只改一个部件时，其余内容部件逐字节相同。关系部件和 `[Content_Types].xml` 总是重新生成，内容等价，字节不同。表里的 `rewritten` 在不解析全部部件时都是这个原因。

**类型模型保住了模式里有的全部内容。** 解析全部部件再写回，XLSX 和 PPTX 没有丢任何东西，`mc:AlternateContent` 和 `extLst` 里的扩展也在。属性值会换写法（`1` 写成 `1.0`），元素和属性按模式顺序重排。

**模式里没有的元素会被丢掉。** 样本里那个外来命名空间的元素（`aster:marker`，已在 `mc:Ignorable` 里声明）一解析就没了。BetterOffice 的测试文件里有两个文件带类似的外来元素，结果相同。这正是“我们不认识的内容原样回到文件里”要防的情况。

**对不合模式的输入很严格。** 解析全部部件时，BetterOffice 的 21 个 PPTX 测试文件里有 9 个打不开，报的是模式要求的子元素缺失，比如母版没有 `clrMap`、演示文稿没有 `notesSz`。这些文件 PowerPoint 能不能打开，我没有验证。重复出现的元素（同一个 `w:pPr` 里两个 `w:rPr`）会被去掉一个。

**重新生成的包元数据不是无害的。** 它写出的 `[Content_Types].xml` 在根元素上多声明了一个前缀（`xmlns:pct`），指向默认命名空间已经用着的同一个地址。这是合法的 XML，我的比较器也判它与原文件内容相同。但 macOS 的“快速查看”读带这个声明的 XLSX 会一直卡住不返回。把原文件的这一个部件换成它的版本就能复现，再把那一处声明删掉就恢复正常。它产出的 DOCX 和 PPTX 没有这个问题。Microsoft Office 是否在意这个声明，没有验证。

写样本时还遇到一处：属性用的命名空间前缀如果声明在元素自己身上而不是根元素上，写回时声明会丢，产物成了不合法的 XML。Excel 实际是把这些前缀声明在根元素上的，所以样本改成了那样，这一条没有出现在上面的表里。

### office_oxide

可编辑路径把所有部件按原始字节保存，关系和内容类型重新生成，编辑是在 XML 文本上做查找替换。所以它不会丢东西，也没有模型可言。查找替换会改掉所有出现的地方，不只是目标那一处。它另一条保存路径是从中间表示重新生成文件，按设计就是有损的，这里没有测。

### 编译成本

在这台机器上（Apple M6，12 核，32 GB），从零构建、`opt-level = 1`：

| 构建内容 | 耗时 | CPU 时间 | 内存峰值 | crate 数 | 可执行文件 |
| --- | --- | --- | --- | --- | --- |
| 只有测试框架和 `own layer` | 3.6 秒 | 14 秒 | 0.3 GB | 16 | 1.9 MB |
| 加 BetterOffice | 76 秒 | 543 秒 | 3.7 GB | 110 | 32.8 MB |
| 加 ooxmlsdk | 78 秒 | 315 秒 | 7.3 GB | 43 | 37.1 MB |
| 加 office_oxide | 16 秒 | 89 秒 | 2.1 GB | 48 | 3.2 MB |

三个库连同它们的依赖共 137 个第三方包，许可证都有 MIT、Apache-2.0、BSD、Zlib 这类宽松选项，可以并入本项目。这是按各包声明的许可证字段统计的，没有经过主工作区的 `cargo-deny` 检查。

ooxmlsdk 的 7.3 GB 是单个编译进程的峰值，GitHub 的 macOS 构建机只有 7 GB 内存。因此这个验证工程是独立的工作区，有自己的 `Cargo.lock`，不参与主工作区的构建和 CI，只在它自己改动时由 `.github/workflows/g4-ooxml.yml` 在 Linux 上检查。

## 为什么还不算通过

1. **没有用 Microsoft Office 打开过任何产物。** 通过标准的第一条是“产物在 Microsoft Office 中无修复提示打开”。这台机器上没有 Office。`g4-ooxml export <目录>` 会把样本和每个候选的产物写成文件，需要有人在 Word、Excel 和 PowerPoint 里逐个打开。
2. **样本不是真实文件。** 三份是手写的，128 份是 BetterOffice 的生成脚本产出的。方案要求的是真实语料库。把 Office 保存的文件放进一个目录，作为参数传给 `run` 或 `summary` 即可加入。
3. **`own layer` 只是基线。** 它证明了包级保真和“改一处文字”可以逐字节做到。元素级保真，也就是已建模的节点带着它不认识的子元素一起移动、一起删除，还没有做，要到真正写模型时才能验证。

## 对方案的影响

- 解析层采用方案里的备选方案：包和未知内容的保真由我们自己基于 quick-xml 的层负责。关卡的“未通过时”动作本来就是这一条，现在的数据支持直接这样选，不必等真实语料的结果。已采纳，记录在 [ADR 0001](../../docs/decisions/0001-ooxml-parsing-layer.md)，其中写明了哪些情况下应当重新审视。
- BetterOffice 作为 XLSX 和 PPTX 编解码器的候选成立，DOCX 不成立。方案里“若在 G4 胜出则锁定版本接入”的设想对 XLSX 和 PPTX 仍然有效，前提是注音那个错误被修掉或绕开。
- ooxmlsdk 生成的类型可以作为读取已建模部件时的参考或工具，不能作为保存路径，也不能作为模型。它的编译成本是个实际的负担。
- 关系部件和内容类型列表是否要求逐字节不变，方案里原来没有写。ADR 0001 写明了：要求。两个库都会重新生成它们而不丢内容，但上面“快速查看”卡住的例子说明，内容等价的改写也可能让别的程序读不了。我们自己的层不需要重新生成它们。

## 运行

```sh
cd spikes/g4-ooxml
cargo run -- run                      # 三份内置样本的结果表
cargo run -- summary <目录> ...       # 加上目录里的文件，只看汇总和丢失最多的内容
cargo run -- detail betteroffice resave aster.docx   # 一个结果丢了什么
cargo run -- export out/              # 把样本和所有产物写成文件，拿去用 Office 打开
cargo test                            # 34 个测试，含记录的结果
cargo test --no-default-features      # 只测框架和 own layer，几秒钟
```

复现 BetterOffice 测试文件上的结果，把目录换成 cargo 下载目录里的 `betteroffice-{docx,opc,xlsx,docx-edit,pptx-edit,pptx-parse}-0.5.1/tests`。
