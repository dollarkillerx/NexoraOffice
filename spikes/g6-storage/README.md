# G6：存储与恢复

Phase 0 的第六道关卡。要回答的问题：进程在任意时刻被杀掉之后，命令日志能不能把文档完整地带回来。

## 做法

一个恢复目录里放三样东西：

- **命令日志**：SQLite 数据库里的 `journal` 表，WAL 模式。每次编辑是一条记录、一个事务，写进去之后才算确认。
- **检查点**：整篇文档写成一个带校验和的文件。数据库里只存指向它的指针。写完检查点文件之后，在同一个事务里把指针指过去并删掉它之前的日志。
- **已保存的文档**：用户看到的那个文件。先写临时文件、刷盘、再改名，所以任何时刻读到的要么是旧文件，要么是完整的新文件。

恢复时读检查点，再按顺序重放它之后的日志。发现修订号不连续、检查点校验和不对、命令套不上文档，都直接报错，不做任何猜测性的修复。

文档内容不进 SQLite。数据库只有日志和一个指针，符合“不要把所有文件内容都塞进 SQLite”的原则。

## 怎样测

`crash-test` 把同一个可执行文件以 `worker` 模式启动。worker 恢复现场后不停地编辑：追加日志、在标准输出上报告修订号、日志攒够 64 条就做检查点、每 150 个修订保存一次文档。父进程在随机的时刻把它强杀，然后像应用下次启动那样打开恢复目录，逐项检查：

1. SQLite 自带的完整性检查通过。
2. 恢复成功，且恢复到的修订号不低于 worker 已经报告过的最大修订号。低了就是丢了已确认的编辑。最多可以比它高一个：那是已经写进日志、还没来得及报告就被杀的那一条。
3. 恢复出的文本，与父进程从头重新计算每一条命令得到的文本完全相同。命令是种子和修订号的纯函数，所以父进程不需要相信磁盘上的任何东西。
4. 已保存的文档文件完整、校验和正确，内容与它声称的那个修订一致。

强杀的时刻有五分之一故意落在启动后的 3 毫秒内，用来命中恢复过程本身。

## 运行

```sh
cargo run --release -p g6-storage -- crash-test             # 1000 次，每次提交都刷盘
cargo run --release -p g6-storage -- crash-test 1000 normal # 提交时不刷盘
cargo run --release -p g6-storage -- bench                  # 各种刷盘设置下的写入延迟
cargo test -p g6-storage                                    # 含两组各 40 次的强杀
```

## 结果

macOS 27.0.1，Apple M6，2026-11-22，SQLite 3.54（随 rusqlite 编译进来）。

### 强杀测试

| 刷盘设置 | 强杀次数 | 丢失的已确认事务 | 损坏 | 命中启动阶段 | 未及确认但已恢复 | 最多重放 |
| --- | --- | --- | --- | --- | --- | --- |
| `full` | 1000 | 0 | 0 | 176 | 123 | 87 条 |
| `normal` | 1000 | 0 | 0 | 162 | 34 | 74 条 |

两组里已保存的文档各被校验了 998 和 999 次，每次都完整。16 个测试通过，其中 3 个是把上面的强杀测试缩到 40 次，随 `cargo test` 在每个平台上运行。

### 写入延迟

| 操作 | p50 | p95 | 最大 |
| --- | --- | --- | --- |
| 日志追加，`synchronous = normal` | 0.006 ms | 0.013 ms | 0.66 ms |
| 日志追加，`synchronous = full` | 0.028 ms | 0.054 ms | 3.14 ms |
| 日志追加，`full` 加 macOS 的 `fullfsync` | 2.30 ms | 3.95 ms | 9.55 ms |
| 检查点，1 MB 文档 | 5.16 ms | 7.04 ms | 10.62 ms |
| 原子保存，1 MB 文档 | 3.71 ms | 4.02 ms | 5.12 ms |

## 这个结论的边界

**这是进程被杀的测试，不是断电的测试。** 进程被杀时，操作系统已经接收的写入不会丢，所以三种刷盘设置都能通过。断电时情况不同：

- `normal` 可能丢掉最近的若干次提交。
- 在 macOS 上，`full` 用的普通 `fsync` 并不要求磁盘清空自己的缓存，只有 `fullfsync` 才能保证断电后数据还在。
- 断电无法在这台机器上用软件模拟，这一项没有验证。

其他没有覆盖的：磁盘写满、文件被别的程序占用或改动、多个进程同时打开同一个恢复目录、Windows 和 Linux。

## 实测中发现的问题

- **检查点不能按“修订号是整倍数”来触发。** 最初是每逢 64 的倍数做一次检查点。检查点比日志追加慢得多，强杀很容易落在它上面，被打断之后要再等 64 个修订才重试。连续被打断几次，日志就越攒越长，测到单次恢复重放了 896 条。改成“日志攒够 64 条就做”之后，被打断的检查点会在下一次编辑时立刻重试，重放量稳定在 87 条以内。
- **真正能扛断电的刷盘要 2 到 4 毫秒一次。** 如果每次按键都同步等它，打字的处理时间会翻倍。日志写入必须放在存储线程上，把短时间内的几条命令合成一个事务提交，界面不等它返回。
- **强杀后会留下没人引用的检查点文件。** 进程死在“写完文件”和“改指针”之间，或者“改完指针”和“删旧文件”之间，都会留下一个孤儿文件。每次打开恢复目录时清理一遍。

## 对正式实现的建议

- 日志由存储线程批量提交。断电时最多丢最后一批，这个窗口要写进产品说明。
- 检查点和文档保存用 `fullfsync`，日志用 `full`。
- 命令的编码从第一天起就带版本号，恢复时遇到不认识的版本要明确报错。
- 恢复失败时保留现场，不要覆盖或删除任何文件。
